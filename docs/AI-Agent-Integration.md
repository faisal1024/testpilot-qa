# TestPilot QA — AI Agent Integration

> Status: Approved — aligned to *Updated Plan After Claude Review*
> Goal: Make TestPilot projects the easiest Playwright projects for AI coding agents to understand and contribute to — and make TestPilot itself agent-callable.

> **Alignment note (approved plan):** MVP generates the agent context files **from one canonical
> source** as part of `init` (no LLM calls — agent *readiness*, not AI-generated tests). The
> standalone `add ai` regeneration command + full drift reconciliation are **V1**. The **MCP server
> is V2 and optional** — Direction 1 (generated files, §1) is the MVP path.

> **Implemented (Milestone 5A):** `@testpilot/ai` defines the canonical guidance once
> (`CANONICAL_GUIDANCE`) and deterministically generates `CLAUDE.md`, `AGENTS.md`,
> `.github/copilot-instructions.md`, and `.cursor/rules/testpilot-playwright.mdc`. `testpilot init`
> writes them by default (selectable via `config.ai.agents`), with the standard overwrite protection
> (`--force`). Each file carries a `version + sha256` marker (`@testpilot/guidance …`) and exported
> helpers (`parseGuidanceMarker`, `isGuidancePristine`) so **5B** can add `doctor` drift detection
> cleanly. The guidance is honest about Tier 1 limits (no DOM-aware suggestions, no auto-fix, no LLM).

## 1. Two Directions of Integration

There are two separate concerns, often conflated. TestPilot does both, deliberately:

1. **TestPilot → Agents (context generation).** TestPilot generates and maintains the context files agents read (`CLAUDE.md`, `AGENTS.md`, `copilot-instructions.md`, Cursor rules) so any agent working in the repo writes *good Playwright by default*.
2. **Agents → TestPilot (tool consumption).** TestPilot exposes structured, machine-readable output (`--json`, SARIF) and a programmatic API so an agent can *call* the analyzer, read findings, and apply fixes as part of its own loop.

Direction 1 is prevention (the agent writes good locators from the start). Direction 2 is correction (the agent runs analysis and fixes what exists). Both are needed.

---

## 2. The Single Source of Truth Problem

The biggest risk in multi-agent support: four files (`CLAUDE.md`, `AGENTS.md`, Cursor rules, Copilot instructions) drifting out of sync, each telling agents something slightly different.

**Recommendation:** TestPilot maintains **one canonical content source** — `testpilot/agent-guidance.md` (or a structured `agent-guidance` block in config) — and *generates* each tool-specific file from it. The per-tool files carry a generated-marker header:

```
<!-- GENERATED by TestPilot QA — edit testpilot/agent-guidance.md, then run `testpilot add ai all` -->
```

`testpilot doctor` warns when a generated file has drifted from its source. This keeps the AGENTS.md / CLAUDE.md ecosystem fragmentation from becoming the user's maintenance burden.

> **Note on AGENTS.md:** treat `AGENTS.md` as the emerging cross-tool standard and the primary artifact; `CLAUDE.md` and `copilot-instructions.md` are tool-specific renderings of the same guidance. Where a tool reads `AGENTS.md` natively, prefer a symlink/import over duplicated content.

---

## 3. What the Guidance Contains

The generated guidance teaches agents the project's conventions so generated tests pass review on the first try:

1. **Locator hierarchy** (from `Locator-Intelligence-Design.md` §2) — "always prefer `getByRole`/`getByLabel`; never XPath, class, or `nth-child`."
2. **Project structure** — where tests, page objects, fixtures, and API clients live.
3. **Patterns to follow** — POM style, fixture usage, web-first assertions, no hard waits.
4. **Commands** — how to run tests, how to run `testpilot analyze` before declaring done.
5. **Definition of done** — "a change is complete only when `testpilot analyze` passes the project's `minScore`."
6. **Anti-patterns** — concrete bad/good examples the agent should never reproduce.

The closing instruction matters most: agents are told to **self-check via `testpilot analyze --json` before finishing**, turning TestPilot into the agent's own quality gate.

## 4. Per-Tool Support

### 4.1 Claude Code (`CLAUDE.md`)

- Generated at repo root (and/or `e2e/CLAUDE.md` for the test subtree).
- Includes the locator hierarchy, project map, and a **"before you finish" checklist** that runs `testpilot analyze`.
- Documents TestPilot's CLI so Claude Code invokes `analyze`/`fix` correctly.
- **MCP server (V2):** ship an optional TestPilot MCP server exposing `analyze`, `explain`, and `suggest-locator` as tools, so Claude Code can query locator intelligence interactively instead of shelling out. This is the highest-leverage Claude-specific integration.

### 4.2 Codex (`AGENTS.md`)

- `AGENTS.md` is the canonical, tool-neutral file; Codex reads it natively.
- Same guidance content; phrased tool-neutrally.
- Emphasize deterministic commands and exit codes (§6) since Codex-style agents lean on scripted verification.

### 4.3 Cursor (`.cursor/rules/*.mdc`)

- Generate **scoped rule files** under `.cursor/rules/` using Cursor's MDC format with `globs` front-matter, so locator rules activate when editing `*.spec.ts`.
- Split: a `locators.mdc` (always-on for test files) + `project-structure.mdc`.
- Keep each rule file short and imperative — Cursor rules work best as terse directives, not prose.

### 4.4 GitHub Copilot (`.github/copilot-instructions.md`)

- Generate repository custom instructions with the locator hierarchy and project conventions.
- Copilot benefits most from **example-driven** instructions (bad → good pairs), since it pattern-matches; include a compact examples block.
- Optionally generate path-specific instructions for the test directory.

### 4.5 Generic / future tools

A `ContextGenerator` interface (Architecture §9) lets new agent formats be added without touching core. Each generator transforms the canonical guidance into a tool-specific file.

## 5. Recommended Repository Structure

A TestPilot-scaffolded project (the `ui-api-fullstack` template):

```
my-automation/
├─ AGENTS.md                      # canonical agent guidance (tool-neutral)
├─ CLAUDE.md                      # generated → imports/derives from AGENTS.md
├─ .github/
│  ├─ copilot-instructions.md     # generated
│  └─ workflows/e2e.yml           # generated CI: test + `testpilot analyze` gate
├─ .cursor/
│  └─ rules/
│     ├─ locators.mdc             # generated, scoped to *.spec.ts
│     └─ project-structure.mdc    # generated
├─ testpilot/
│  └─ agent-guidance.md           # SINGLE SOURCE for all generated agent files
├─ testpilot.config.ts            # rules, scoring, AI agents, template config
├─ playwright.config.ts           # plain Playwright (ejectable)
├─ tests/
│  ├─ ui/
│  │  └─ login.spec.ts
│  └─ api/
│     └─ users.spec.ts
├─ src/
│  ├─ pages/                      # Page Objects (POM)
│  │  └─ LoginPage.ts
│  ├─ api/                        # typed API clients
│  │  └─ UsersClient.ts
│  └─ fixtures/                   # Playwright fixtures (auth, data)
│     └─ index.ts
├─ test-data/                     # factories / fixtures data
└─ package.json
```

Principles encoded by the layout:
- **Tests vs. infrastructure separated** (`tests/` vs `src/`) — agents and humans find things predictably.
- **Page Objects and API clients are first-class** — agents extend existing patterns instead of inventing new ones.
- **One guidance source, many generated files** — no drift.
- **Plain Playwright config** — nothing hidden; ejectable.

## 6. Agent-Facing Output Contract

For Direction 2 (agents calling TestPilot), the contract is the stable `--json` envelope (CLI-Spec §5) plus:

- **SARIF** output so findings appear as GitHub code-scanning annotations on agent PRs.
- **Stable `ruleId`s and `docsUrl`s** so an agent can fetch the rule explanation and reason about the fix.
- **`autoFixable` flag** so an agent knows which findings it can resolve via `testpilot fix` vs. which need judgment.
- **Documented exit codes** so an agent's scripted loop can branch on "quality gate failed" (`1`) vs "operational error" (`2–5`).

Recommended agent loop, which the guidance files describe explicitly:

```
write/modify test
  → testpilot analyze --json
  → if findings: testpilot fix --write (auto-fixable) ; address the rest by hand
  → re-run analyze until score ≥ minScore
  → run playwright test
  → done
```

## 7. MCP Server (V2 — optional)

> Deferred to V2 per the approved plan ("possible MCP server"). MVP and V1 rely entirely on the
> generated context files (Direction 1). Ship MCP only once Tier-2 DOM analysis makes interactive
> queries worth the added maintenance surface.

Beyond static files, ship `@testpilot/mcp` exposing tools:

| MCP tool | Purpose |
|---|---|
| `analyze_tests` | Run Locator Intelligence over given files; return findings JSON. |
| `explain_rule` | Return a rule's rationale + examples. |
| `suggest_locator` | Given a DOM/trace + intent, return a ranked resilient locator. |
| `score_project` | Return current quality score + sub-scores. |

This turns "agent-friendly" from passive (files the agent reads) into active (capabilities the agent calls), and is the cleanest long-term integration surface across *all* MCP-speaking agents at once — rather than maintaining N bespoke per-tool integrations.

---

## 8. Anti-Patterns to Avoid

- **Don't** hand-maintain four divergent instruction files — generate from one source.
- **Don't** make AI features mandatory — the analyzer and scaffolder must work with zero API keys and zero network.
- **Don't** let generated agent files overwrite user edits silently — mark them generated and warn on drift via `doctor`.
- **Don't** dump the entire rule catalog into context files — agents need the *hierarchy and a few examples*, not 40 rule pages. Link to docs for depth.
- **Don't** assume one agent ecosystem wins — invest in the neutral `AGENTS.md` + MCP, render the rest.
